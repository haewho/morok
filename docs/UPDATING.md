# Перенос upstream и обновление APK

Перед переносом прочитайте `AGENTS.md`, lock, `HOOKS.md`, `MEMORY.md`, `FEATURE_PARITY.md` и `PROGRESS.md`. Сохраните коммиты текущего состояния и резервную копию данных/подписи. Проверьте официальный release, gradle.properties, refs и SHA заново. Текущий `master` не считается стабильным только по имени.

`scripts/prepare-upstream-update.sh <проверенный-ref>` создаёт отдельную `codex/upgrade-*` ветку и worktree. Скрипт не делает автоматического merge и не меняет lock до проверки. В новом worktree выполните `git merge --no-ff <проверенный-SHA>`, разрешите конфликты по смыслу, затем обновите submodules. Для shallow checkout при необходимости получите недостающих предков.

Проверяйте не только конфликтующие строки, но все символы в `HOOKS.md`: сообщения/difference, жизненный цикл аккаунтов, эффекты, навигацию и прокси. Перенесите связанные TL-схемы, ресурсы, native зависимости и toolchain вместе. Сверьте release notes и отставание публичных исходников. После тестов обновите lock и матрицу; сравните с предыдущей сборкой на устройстве и в отдельной сети.

Сохраняйте applicationId и release certificate. VersionCode должен расти; ныне upstream схема `7038*10+9=70389`. До первого распространяемого релиза установите собственную политику увеличения mod versionCode для нескольких релизов на одной upstream-базе. Системное обновление APK не заменяет миграции локальных данных. Автообновление от серверов Telegram выключено; собственного проверенного APK-updater пока нет.

Восстановление исходников: вернуться к сохранённой ветке/коммиту. Восстановление данных: только проверенный экспорт и совместимая схема. Обычный downgrade APK после миграции не гарантируется. Сам процесс переноса между двумя разными upstream-версиями ещё не проверен; запуск скрипта на том же SHA не является таким тестом.
