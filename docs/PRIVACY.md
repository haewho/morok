# Экспериментальная приватность

Все настройки выключены по умолчанию и хранятся отдельно для устойчивого Telegram user ID. MOROK не обещает состояние «всегда офлайн»: отправка сообщения, звонок, серверная логика и другая активная сессия могут раскрывать присутствие. Подавление online/read/typing конфликтует с пунктом 1.4 правил Telegram API; отдельная настройка не устраняет этот конфликт.

## Фактическая реализуемость

| Поведение | Состояние в этой версии | Ограничение |
|---|---|---|
| Штатные настройки «Последняя активность» Telegram | Сохранены | Серверная политика Telegram; MOROK её не подменяет |
| Набор, запись, загрузка, выбор стикера | Реализовано локальное подавление | Семантический gate в `MessagesController.sendTyping`; результат со второго аккаунта ещё не проверен |
| Emoji interaction / просмотр интерактивной emoji-анимации | Реализовано локальное подавление | Обычный центральный action и отдельная отправка taps охвачены |
| Cancel typing | Всегда разрешён | Нужен, чтобы включение режима не оставляло прежний индикатор до timeout |
| Speaking in group call | Не подавляется | Это часть работающего call signaling, а не обычный индикатор набора чата |
| Server-required bot draft cleanup | Не подавляется | Служебное завершение draft должно сохранять согласованное состояние |
| Обычный foreground online status | Реализовано локальное подавление | Lifecycle/reconnect timer не отправляет `offline=false` и один раз использует штатный `offline=true`; результат со второго аккаунта ещё не проверен |
| Обычный read receipt и локальный cursor | Реализовано разделение для обычных чатов | Локальные сообщения, counters, badges и notifications очищаются без server request; secret chats не подавляются; restart и второй аккаунт ещё не проверены |
| Content read для входящих voice/round video | Реализовано локальное подавление | Локальный played-state сохраняется; обычный read cursor управляется отдельной настройкой, secret/TTL и прочие content types не меняются; результат со второго аккаунта ещё не проверен |
| Story read/view | Реализовано локальное подавление | Локальные `max_read_id`/album cache и UI обновляются, `stories.readStories`/`incrementStoryViews` не отправляются; реакция или ответ остаются явными серверными действиями и могут раскрыть просмотр |
| Read-on-reply | Реализована opt-in синхронизация | Выключено по умолчанию; только успешный немедленный ответ на входящее сообщение отправляет cursor, ошибки/редактирование/расписание/secret chat исключены |
| Исключение чата | Реализовано для поддержанных chat-scoped политик | Возвращает обычные typing/read/content-read/story-view для выбранного чата; online-status остаётся account-wide; переключатель находится в контекстном меню сообщения |
| Отложенная Ghost-отправка | Реализована как отдельный opt-in | Поддержанные сообщения ставятся в серверное расписание на одну минуту, очередь сразу видна и допускает отмену; неподдержанная отправка останавливается, а не переходит к немедленной |
| Отправка сообщения без появления online | Не заявляется | Расписание может уменьшить немедленное раскрытие присутствия, но эффект требует собственного API ID и наблюдения вторым аккаунтом |

Пресет «Призрак» сейчас включает реализованные политики набора, обычного foreground online-status, обычного server read cursor, content-read для входящих голосовых и круглых видеосообщений и story views. Индивидуальные переключатели хранятся отдельно: отключение пресета не стирает выбранные вручную политики. Read-on-reply и минутная отложенная отправка не входят в пресет и остаются явными opt-in; задержка действует только пока сам пресет включён. До 256 исключений чатов хранятся вместе с настройками устойчивого Telegram user ID; исключение имеет приоритет над chat-scoped политиками пресета, ручными флагами и задержкой отправки, но не меняет общий online-status.

Typing gate возвращает `false` до создания MTProto request и до изменения локального `sendingTypings`. Online gate проверяется в штатном status timer до ветки `TL_account.updateStatus(offline=false)`; при включении политики следующая итерация отменяет незавершённый online request и использует существующую offline-ветку. Content-read gate срабатывает только для `isVoice()`/`isRoundVideo()` после локального обновления БД/UI и до создания сетевого request. Подавленное событие не накапливается и не отправляется после выключения режима. Для сообщения с mention Telegram использует тот же content-read request, поэтому mention может остаться непрочитанным на сервере, хотя локально будет снят. Secret и self-destruct paths не подавляются.

Эти gates не отбрасывают произвольные пакеты, не подделывают успешный ответ сервера и при ошибке чтения настроек сохраняют обычное поведение Telegram. Быстрый ответ из уведомления, ChatActivity, voice/video recording, upload progress и sticker selection используют центральный typing-путь. Воспроизведение из основного media controller и popup-аудио использует центральный content-read путь. Прямые call/bot actions рассмотрены отдельно в таблице.

Read gate сохраняет штатные локальные `processPendingRead`, dialog counters и очистку уведомлений, но не создаёт `readHistory`/`readDiscussion`/`readSavedHistory` task для обычного чата. Повторная проверка перед отправкой отбрасывает task, которая уже ждала штатные пять секунд в момент включения режима. Подавленные cursors не образуют очередь и не отправляются сразу при выключении. Следующее обычное чтение после выключения продвинет серверный max-id и тем самым охватит более старые сообщения, как требует cursor-протокол Telegram.

Явное действие «Отметить прочитанным» в списке чатов или тем, notification action и Android Auto отправляет server cursor даже при включённой политике. Автоматическое открытие/закрытие ChatActivity, popup notification и отправка ответа из Wear/Android Auto используют обычный gate. Mentions, reactions и content-read являются отдельными server events и управляются своим штатным либо отдельным MOROK-путём. Входящие read updates другой активной сессии обрабатываются штатно и могут продвинуть локальное состояние.

При включённом read-on-reply центральный `SendMessagesHelper` ждёт успешного ответа на фактическую отправку. После этого он синхронизирует cursor только до входящего сообщения, на которое ответили; для forum topic используется его thread ID. Такая синхронизация не запускается заранее, при неудачной отправке, редактировании, scheduled message или secret chat. Быстрые ответы, которые не несут доступный объект исходного сообщения, продолжают обычное поведение своего read gate.

При включённой задержке центральный `SendMessagesHelper` до создания локального сообщения задаёт серверное расписание Telegram на текущий серверный timestamp плюс 60 секунд. Штатный экран scheduled messages открывается после постановки из обычного чата и предоставляет отмену. Уже запланированное пользователем сообщение не переносится повторно. Повторная отправка ошибки, secret chat, welcome/quick reply, TTL и one-shot/ephemeral, платное сообщение, story reply/publication, suggestion post, live location, dice, mono forum и главный экран forum без выбранной темы останавливаются с уведомлением; немедленной запасной отправки нет. Реальная невидимость не обещается: Telegram может раскрывать активность другими сигналами, а наблюдение собеседником ещё не выполнено.

Story gates стоят после локального обновления списка просмотренного и до двух фактических protocol requests: `stories.readStories` и `stories.incrementStoryViews`. Подавленные просмотры не копятся для последующей отправки. Реакции, ответы, публикация и действия другой сессии не подавляются этим переключателем; UI прямо сообщает это ограничение.

Проверка на JVM покрывает выключенные defaults, независимость пресета и индивидуальных typing/online/read/content-read/story-view/read-on-reply настроек, включение и приоритет исключения для Ghost-задержки, сохранение chat exceptions, разрешение cancel, reset, schema downgrade и разделение аккаунтов. Компиляция Android подтверждает совместимость hooks/UI. Фактическую видимость online, typing, read, content-read, story-view, read-on-reply и scheduled send для собеседника нужно проверить вторым аккаунтом на другом устройстве после настройки собственных Telegram API credentials.
