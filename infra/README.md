# Инфраструктура прокси Морока

В этом каталоге подготовлены шаблоны и локальные инструменты. Реальные узлы, ключи, домены и публичный deployment отсутствуют. Пример с `REPLACE_*` намеренно не является работающей конфигурацией.

Для первой инфраструктурной реализации выбран [9seconds/mtg v2.2.1](https://github.com/9seconds/mtg/tree/dc81f7981c6b3cf132341204f0310662826826a0), SHA `dc81f7981c6b3cf132341204f0310662826826a0`, с поддержкой FakeTLS. Ref проверен 6 сентября 2026 года; запись — `mtg.lock.json`. Минимальная версия Go из закреплённого `go.mod` — 1.26. Это выбор для воспроизводимой подготовки, а не результат испытаний в российских сетях.

Также изучен [официальный MTProxy](https://github.com/TelegramMessenger/MTProxy): это альтернативная реализация, а не второй клиентский стек. Его README отмечает устаревший готовый Docker image, поэтому плавающий официальный image здесь не закрепляется. Android-клиент использует собственный штатный транспорт Telegram. FakeTLS не гарантирует устойчивость к блокировкам.

## Подготовка двух узлов

На Linux с проверенным локальным Go 1.26+ можно собрать закреплённый исходник:

```sh
sh infra/build-mtg.sh /path/to/new/mtg-source
```

Скрипт только клонирует закреплённый commit и собирает локальный бинарник. Он не устанавливает пакет и не запускает публичную службу. Go-зависимости проверяются по upstream `go.sum`; SHA-256 полученного бинарника записывается рядом. Для воспроизведения сохранить фактическую patch-версию Go, ОС/архитектуру, SHA бинарника и логи сборки. Сам серверный бинарник в этой сессии не собирался.

Для каждого независимого узла оператор подготавливает отдельный секрет (`morok-mtg generate-secret --hex <собственный подходящий TLS-домен>`), копию `mtg.toml.example`, непривилегированного пользователя `morok-proxy` и unit `morok-mtg.service`. Секрет хранится в `/etc/morok/mtg.toml` с доступом только root и пользователю службы. Инструкции CLI и параметры сверены с [README закреплённой версии](https://github.com/9seconds/mtg/blob/dc81f7981c6b3cf132341204f0310662826826a0/README.md) и [примером конфигурации](https://github.com/9seconds/mtg/blob/dc81f7981c6b3cf132341204f0310662826826a0/example.config.toml).

Шаблон отключает debug и удалённые blocklist-загрузки, использует системный DNS, ограничивает соединения и оставляет Prometheus на `127.0.0.1:3129`. Публично нужен только согласованный порт прокси; административный SSH и метрики не публикуются как часть сервиса. Конкретные firewall/VPS/DNS-команды выполняются только после выбора владельцем инфраструктуры.

Серверные проверки процесса/порта/Prometheus полезны для диагностики, но рабочим узел считается после протокольной проверки с телефона в нужной сети. Проверить отправку файла и разные DC, затем отключение одного узла. Второй адрес на том же сервере не подтверждает независимость резерва.

## Подпись пула

Создать собственный RSA-ключ вне репозитория и CI внешних PR, например OpenSSL:

```sh
openssl genpkey -algorithm RSA -pkeyopt rsa_keygen_bits:3072 -out /secure/location/pool-key.pem
openssl pkey -in /secure/location/pool-key.pem -pubout -outform DER -out /secure/location/pool-public.der
openssl base64 -A -in /secure/location/pool-public.der
```

Последняя команда выдаёт только публичный ключ для `key.<id>` в APK trust-файле. Приватный ключ не передаётся через чат и не помещается в APK. Адреса и пароль/секрет узлов являются клиентской конфигурацией, которую APK-пользователь способен извлечь; это не способ хранить административные секреты.

Заполнить `pool.json.example` действительными timestamps, новой монотонной версией и настоящими ссылками двух узлов. Подписать точные байты:

```sh
python3 infra/sign-pool.py --input /private/pool.json --private-key /secure/location/pool-key.pem --key-id owner-2026 --output /private/pool.txt
```

Signer валидирует поля, сроки, уникальность endpoint и тип/размер RSA-ключа; результат — строгий подписанный формат клиента. Подробная схема, защита от отката и порядок ротации ключей находятся в [`docs/PROXY.md`](../docs/PROXY.md).

Публичные ключи и два настоящих HTTPS endpoint добавить в `TMessagesProj/src/main/assets/morok-proxy-trust.properties` по примеру. Начальный действующий `pool.txt` включается в APK под именем `morok-proxy-pool.txt`. Обновляемый файл размещается по обоим HTTPS-адресам после отдельного разрешения на deployment. Нужен ответ `200`, без redirects, с телом не более 96 KiB; приватный ключ остаётся у подписывающей стороны. На сервер публикуются только подпись и данные подключения.

## Проверено локально

`sh infra/test-proxy-core.sh` — 34 проверки Java-ядра; `python3 infra/tests/test_signer.py` — совместимость Python/OpenSSL-подписи и Java-проверки. Тестовые ключи создаются во временном каталоге и удаляются; реальная инфраструктура ими не подписывается. Shell-синтаксис сборочного шаблона и Python-синтаксис signer проверены. Развёртывание MTG, работа узлов и российские сети не проверены.
